1. MODELO ESCOLHIDO

main: versões publicadas do portfólio.
dev: integração das funcionalidades em desenvolvimento.
hml: candidato a release para revisão/validação.
feature/<assunto>: trabalho novo; nasce de dev e retorna a dev.
release/<versao>: estabilização; nasce de dev e é promovida a hml/main.
hotfix/<assunto>: correção urgente de versão publicada; nasce de main.

Não criar branches chamadas apenas feature, release e hotfix para manter para sempre.
Criar uma branch específica quando surgir trabalho, como feature/case2-network.
Dev/hml/main são persistentes. As outras são temporárias.
Este é GitFlow adaptado com hml; não é uma exigência do Terraform.
Branches não criam ambientes AWS, não selecionam tfvars e não separam estado.

Fluxo normal:
dev -> feature/assunto -> PR para dev
 dev -> release/0.0.1 -> PR para hml -> PR hml para main -> tag v0.0.1
 release/0.0.1 -> PR para dev (sincronizar correções da release)

4. BOOTSTRAP — CRIAR BASE COMUM

Um repositório sem commits precisa de um ancestral comum para seus primeiros PRs.

A exceção de push inicial termina depois deste bootstrap.

git branch --show-current
git diff --cached --name-only

# Se houver arquivos staged, retirar do índice antes do commit vazio.
# Não executar commit vazio sem verificar, pois --allow-empty não ignora o índice.

git push -u origin main

# Criar as bases a partir do mesmo commit:

git push -u origin dev
git switch -c hml

Depois, configurar proteção/rulesets no GitHub para main, dev e hml:

Não confundir proteção de branch com aprovação de deploy.

7. PRIMEIRA RELEASE — QUANDO O MARCO ESTIVER PRONTO

v0.0.1 pode identificar a base Terraform + CI, mesmo sem VPC/ECS, desde que a
nota da release descreva esse limite. Não é preciso tag em cada commit.
A versão marca um conjunto revisado de mudanças.

# Depois de integrar as features desejadas em dev:
git switch dev
git pull --ff-only origin dev
git switch -c release/0.0.1
git push -u origin release/0.0.1

Abrir PR release/0.0.1 -> hml. Aguardar CI/revisão e fazer merge commit.
Revisar documentação e resultados; isso não significa testar infraestrutura AWS.
Correções de estabilização são feitas na release, com commit/push e novo PR para hml.
Depois, abrir PR hml -> main, revisar e fazer merge commit.
Não fazer push direto em main para contornar a proteção.

# Atualizar main e confirmar o commit exato aprovado antes de criar a tag:
git switch main
git pull --ff-only origin main
git log -1 --oneline
git tag -a v0.0.1 -m "case2: Terraform base and static CI; no AWS deployment"
git push origin v0.0.1

A tag aponta para o commit; o prefixo v é uma convenção.
Tag não é branch. Criar tag não cria automaticamente uma GitHub Release.
Se desejar, criar uma Release no GitHub usando essa tag e descrever o que funciona,
o que está pendente e quais verificações foram executadas.
O workflow atual não é disparado por push de tags; o check já ocorreu no PR/main.

Sincronizar correções da release: PR release/0.0.1 -> dev, merge commit.
Depois sincronizar main -> dev e dev -> hml por PR se houver commits ainda ausentes.
Essa sincronização mantém ancestrais comuns; não copiar arquivos manualmente.
Evitar squash/rebase nos PRs de promoção entre branches persistentes deste roteiro.

# Depois dos merges e sincronizações, exclusão opcional da release:
git switch dev
git pull --ff-only origin dev
git branch -d release/0.0.1
git push origin --delete release/0.0.1

Se -d recusar, conferir se o trabalho foi integrado; não trocar por -D sem entender.
Branches feature também podem ser removidas após o merge.

8. HOTFIX — SOMENTE APÓS EXISTIR VERSÃO PUBLICADA

Exemplo futuro: erro no workflow da versão v0.0.1.

git switch main
git pull --ff-only origin main
git switch -c hotfix/case2-ci

# Corrigir, revisar e adicionar somente os arquivos pertinentes:
git add .github/workflows/terraform-ci.yml
git diff --cached
git commit -m "fix(ci): correct Terraform validation workflow"
git push -u origin hotfix/case2-ci

Abrir PR hotfix/case2-ci -> main; aguardar checks e fazer merge commit.

git switch main
git pull --ff-only origin main
git tag -a v0.0.2 -m "case2: fix Terraform CI"
git push origin v0.0.2

Depois abrir PR main -> dev e, após merge, dev -> hml para propagar a correção.
Se houver release ativa, sincronizar main -> release/<versao> por PR também.
Resolver conflitos na branch de trabalho e revisar; nunca descartar alterações
para apenas fazer o merge passar. Manter branches persistentes atualizadas.

9. LEMBRETES

- Commit: registra uma mudança. Branch: linha de trabalho. Tag: referência de versão.
- Feature termina em dev; release passa por hml e chega a main; hotfix nasce de main.
- Versões 0.x comunicam evolução inicial; descrever claramente o marco entregue.
- CI atual apenas valida Terraform. Nenhum merge/tag faz deploy AWS.
- Backend e tfvars do ambiente serão selecionados explicitamente se houver CD futuro.
- Não versionar tfstate, planos ou credenciais; não usar git push --force neste roteiro.
- Executar comandos por etapa, não colar este arquivo inteiro no terminal.
